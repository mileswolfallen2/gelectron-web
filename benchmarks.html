Detailed Benchmarks

A deep dive into how Gelectron and Electron compare — with graphs, technical context, and honest caveats.

⚠️

Read This First

Early builds

Both Gelectron and Electron were tested on early, non-optimized builds. These numbers will change significantly as the projects evolve.

Not all features implemented

Gelectron does not yet have memory tracking, auto-updater, native module support, or many advanced APIs. Fewer features means less overhead — these results may not reflect final performance.

Single-run tests

Benchmarks were run once, not averaged across multiple iterations. Real-world performance requires repeated testing with warm-up cycles for accurate results.

Different engines, different strengths

Gelectron uses Servo (Rust); Electron uses Chromium (C++/V8). They optimize for different things. Raw ops/s doesn't tell the whole story.

Technical Deep Dive

Why these numbers look the way they do.

Why is Style Recalc so fast?

Servo uses Stylo, a CSS engine written entirely in Rust. Unlike Chromium's Blink, which processes CSS rules sequentially on a single thread, Stylo partitions the DOM into parallel work units and computes styles across all available CPU cores simultaneously.

This is why Gelectron shows 5M ops/s vs Electron's 365K ops/s — a 13x difference. On a multi-core machine, this translates to dramatically faster page loads and re-renders.

Why does Electron win querySelector?

Chromium's DOM has been optimized for decades. Its internal hash-based selector matching and bloom filter pre-filtering are extremely mature. Servo's query engine is newer and doesn't yet have the same level of optimization.

This gap is expected to close as Servo's DOM API matures. The raw query performance matters less in real apps than the style recalc performance, since queries usually trigger re-renders.

SpiderMonkey vs V8 — JS engines

Gelectron uses SpiderMonkey (Firefox's JS engine) while Electron uses V8 (Chrome's JS engine). Both are world-class JIT compilers.

In these benchmarks, SpiderMonkey edges ahead on recursive calls (Fibonacci) and sorting, while V8 is competitive on parsing. In practice, the JS engine difference matters less than the rendering engine difference for most desktop apps.

WebRender vs Skia — GPU rendering

Both engines use GPU-accelerated rendering but with different approaches:

WebRender (Servo/Gelectron) treats the page as a texture and composites it on the GPU with minimal CPU involvement. It was designed for power-constrained devices.

Skia (Chromium/Electron) is Google's 2D graphics library. It's mature and well-optimized but involves more CPU-side preparation before GPU handoff.

The Canvas 2D benchmark reflects this — Gelectron's 2.5M ops/s vs Electron's 2.05M ops/s shows WebRender's leaner pipeline.

Why is Electron's memory so high?

Chromium's architecture bundles its own GPU process, utility processes, and extensive infrastructure for features like site isolation, sandboxing, and crash reporting. Even a minimal Electron app starts with ~200 MB RSS.

Servo was designed for embedding — it doesn't carry the same overhead. We expect Gelectron's final memory footprint to be a fraction of Electron's, but we can't confirm this until memory tracking is implemented.

What these benchmarks don't tell you

  • Real-world app performance — these are microbenchmarks, not full apps
  • Startup time — not measured here
  • Plugin compatibility — many npm packages won't work yet
  • Rendering accuracy — Servo may not render all CSS perfectly yet
  • Long-running stability — not tested

Final Disclaimer

These benchmarks are from very early builds of a non-commercial, community-driven open source project. They are not averaged, not statistically validated, and not representative of final performance. Gelectron does not yet have all features implemented. Take these numbers as a rough directional signal only.
